# 動作・観測取得・推定・IKの非同期実行

2026年10月17日の追加指示を記録する。身体を壁時計で動かし、その間に観測を集めて推定する。推定が終わるまでの間も、最新の完了済みKと保持した身体分布を使ってIKを繰り返し、短い動作をつなぐ。この方式を既定の `async` として実装し、半速設定の別sourceで実配信を検証した。同期方式のテストやsource hashとの対応は分けて保持する。最終結果は末尾の実測節と [検証記録](validation/async_execution_20261017.json) に記録する。

## 実行周期とprocessの分離

| 処理 | 要求する周期・役割 |
| --- | --- |
| 物理身体と実送信指令 | 20 Hzを目標とし、50 ms刻みで速度・加速度・関節限界・停止距離を守る |
| カメラ取得 | 15 fpsを目標とし、取得時点の画像・IMU・送信指令を対応付けて保存 |
| 推定worker | 選択した新取得を逐次融合。処理中でも物理・取得・制御を待機させない |
| 制御worker | 約3 Hzを目標に、保持分布と最新の完了済みKから完全な規準の勾配を一回更新 |
| 表示・記録 | 実際に使った同じ候補のsource ID、指令、時刻、版、遅延を公開 |

これらは要求する周期であり、Python・OS上の厳密なhard real-time保証ではない。実際の周期、期限遅れ、推定・制御の処理時間、観測と表示の遅延をそれぞれ測る。従来のシミュレーションdtを、そのまま実測Hzと表示しない。

推定と制御を別processへ分け、可変URDFモデル、Pinocchio等の計算用data、平衡計算の状態・キャッシュを共有しない。物理側の真のモデルも推定・制御側へ渡さない。通信する候補は不変のsnapshotまたはその同じパラメータのコピーとし、コピー後もsource IDと全値が一致することを確認する。

新しい既定の `execution_mode` は `async` とする。同期の `live` と事前計算を再生する `prepared_playback` は、明示的な診断経路として保持する。同期の実公開Hzと、非同期の物理・カメラ・推定・制御それぞれのHzを混同しない。

## 全取得の保存と融合する取得の選定

推定workerが処理中でも、実際に取得した全raw画像・IMU・送信指令を保存する。画像は観測生成側のブラー等を含む実入力であり、真の角点や姿勢による補完・描き直しを行わない。保存した画素、画像hash、IMU、送信指令と観測時刻を対応付ける。

raw画像保存と2Dの緑枠preview検出は専用threadで行う。previewの検出は画像平面の補助表示であり、推定した姿勢候補ではない。再接近にはpreviewだけでなく、新しい実融合済み全目標をactive IKへ採用済みであることを要求する。取得予定でない物理frameでは画像を生成せず、画像を空・画像stampを未定義として記録する。

取得ごとに、少なくとも次の情報を保存する。

- 一意なcapture IDと取得順序。
- 観測時刻、対応する実送信指令、物理側の取得時刻。
- 画像の保存先とhash、同じ取得のIMU入力。
- 推定へ選択したか、未融合としたか、その理由と選定時刻。

workerがreadyになったら、その時点で利用可能な最新取得を選ぶ。処理待ちの古い取得を後から全件融合したとは説明しない。新しい取得に置き換えたものや処理終了まで選ばれなかったものは、選定logで明示する。保存されていることと、推定情報として取り込まれたことは別である。

選んだ取得の全センサ・全観測成分は、既存の共通事前補正融合へ一度だけ渡す。同じIDを再送・再表示して情報として重複計上しない。Bayes Factor Surpriseの変化事前確率0.25も、新しく取り込んだ有効packetにつき一度であり、物理20 Hzや全raw取得数に対して適用しない。画像未検出と全観測欠落の扱いは、既存の [逐次更新要件](REQUIREMENTS_SEQUENTIAL_UPDATE.md) に従う。

## 保持事後と実指令のledger

workerを呼ぶたびに独立な初期身体を作り直してはならない。前回の単一内部事後、未知マーカーを含む全共同共分散、全交差、固定目標、剛性の累積記憶を保持する。身体の明示的なkeep/reset変化kernelは [Bayes Factor Surprise仕様](BAYES_FACTOR_SURPRISE.md) のまま使う。

推定が処理中の区間も、実際に送信した全指令をledgerへ追記する。各区間には、始点・終点の時刻と実指令、その区間に使った凍結Kと指令作用の出自を持たせる。制御workerが提案した未実行の目標位置を、実際の身体が到達した指令として伝播しない。

推定workerが次の観測時刻へ事前を運ぶ際と、遅着した事後を現在へcatchupする際には、この全区間を順に使う。区間内の作用は、保持身体に対する既存の `theta_eq(q,K)-theta_eq(c,K)` の右作用と、同じ全共分散の輸送である。途中のK更新を捨て、最新K一つで過去を置き換えない。Kから身体候補を再生成しない。

固定根元目標の周辺・全質量・取得元記録は保持し、身体側と全交差を同じ区間作用で運ぶ。新しいマーカー観測だけが、その全観測成分によって目標mixtureを更新する。内部の単一代理と、観測側・規準の `p_goal` のmixtureを引き続き区別する。

遅着結果を適用する際は、観測時の指令・版からどのledger区間を通ったかを記録する。古い結果のmetadataだけを現在時刻・現在指令へ書き換え、輸送したことにしてはならない。

## 推定待ち中のIKと物理動作

制御workerは、最新の完了済み推定分布とKを受け取り、完全な規準のGaussian正規化項、Bingham正規化項、全目標成分のlog-sum-expを含む勾配で、一回の短い更新を選ぶ。推定が未完了でも保持分布を実指令へ運び、同じ基準で更新を続ける。真のリンク姿勢・スイッチ位置・Kや、少数の状態サンプルを用いた代理規準へ置き換えない。

物理側は50 ms周期を目標に、実際の壁時計経過dtで、その時点で利用可能な所望速度へ制約内でつなぐ。通常速度上限0.048 rad/s、加速度上限0.30 rad/s²、URDF関節限界と停止距離を守る。探索時は同じ指令制約の下で最大0.0125 rad/sとし、停止中心と振幅の拡大規則を維持する。制御結果の選定元の時刻・指令と適用時刻も別に記録する。完了したIK計画の有効期間は採用時点から0.5秒とし、次の計画が間に合わなければ同じ加速度制約で減速する。

新しい推定結果はpendingとして保持し、制御workerが返した身体分布・K・IK・snapshotの一組をatomicにactiveへ採用する。推定がIKを追い越すたびに計画を棄却して動作を停止させないため、完了計画はactiveの取得より新しいか同じなら採用し、次の要求には最新の推定を使う。最新推定captureとactive IKのcaptureは別に公開し、物理の指令作用にはactiveのK packetを用いる。Kのない初期全欠測・観測なしでは、宣言済みの直接指定候補族の右作用を使い、未選定のKを作らない。

マーカー喪失時は接近を減速停止し、最初の0.25秒静止、停止中心での有界な振幅拡大型探索、各中心帰還後の0.25秒静止を行う。推定やIKが別processになったことを、真値による探索・再接近や分布の置換の理由にしない。再検出の新しい全観測成分で固定目標を更新してから接近へ戻る。実際に実行した `command_interval_mode == searching` の軌跡区間だけをオレンジ色にする。

## 三つの時刻と表示する候補

以下の時刻を区別する。

| 時刻 | 意味 |
| --- | --- |
| observation stamp | 推定へ入力したraw取得の時刻 |
| prediction stamp | その候補を実指令ledgerで運んだ先の時刻 |
| physical stamp | 表示・記録している物理身体の時刻 |

処理完了時刻・公開時刻と、それぞれの遅延も記録する。画像を再利用しただけでobservation stampを更新しない。固定目標の取得元stampと、現在の身体・交差を照会するprediction stampも別に保持する。

IKとsnapshotの候補は、身体・目標の全パラメータ、全mixtureとlog weight、source ID、指令、版、prediction stampを照合する。異なるprocessでのコピーも、この同じ候補のコピーであることを確認する。描画だけを物理真値へ再中心化したり、遅延を隠すための分布を作ったりしない。

実物理と候補の表示時刻が異なる場合は遅延を表示する。新しい物理frameへ古い候補を無説明で重ね、現在の推定と呼ばない。RViz設定、画像・点のサイズ、レイアウト、視点、標本数は変更せず、保存した設定とバイト単位で比較する。物理TFは20 Hzを目標に送信し、重いscene幾何の描画は既存の `display.publish_hz` の10 Hzで行う。候補のsnapshot・分布wire・剛性は同じ制御計算の完了ごとに公開し、これらを物理20 Hzの更新と説明しない。

## 30壁時計秒の終端とfinal captureのdrain

実験の物理動作は30壁時計秒で終了する。終了後は新しい動作を実行せず、既に取得した最終captureを推定workerが処理し終えるまでdrainする。最終取得IDと最終処理済みcapture IDを照合し、有効成分の融合と欠測による恒等更新を区別する。処理のために物理実験時間を延長したり、最後の未処理観測を黙って除外したりしない。

画面とmetadataで、物理動作の終了、推定処理中、最終取得の推定完了を区別する。30秒で身体が止まったことを探索の打ち切りと呼ばず、推定workerが終了していないことを物理動作の継続と呼ばない。

## 新しいsourceでの検証条件

既存の同期progressive実装は323テストと両ケース各601周期で検証した。結果は [同期実装の記録](validation/progressive_search_20261017.json) に保存した。このsource snapshot、同じ候補の照合、同期Hzは、非同期化したsourceへの検証結果ではない。

非同期方式では次を改めて確認する。

- 推定workerを遅らせても物理・画像取得が進むことと、実際の各Hz・周期分布・期限遅れ。
- 全raw取得の保存、選択・未融合logの完全な対応、選択した新観測IDの一回だけの融合。
- 全実指令ledgerと区間ごとの凍結K、遅着結果のcatchup、全交差・固定根元目標の保持。
- 異なるprocessの可変モデルの分離、同じ候補source IDと全値、IK・実snapshot・公開wireの一致。
- 物理制約、振幅拡大型探索、中心静止、実行区間ごとのオレンジ色と通常軌跡の保持。
- 30壁時計秒の物理終了、最終取得のdrain完了、画面・metadata・保存記録の対応。
- 真値が推定・制御に入らないこと、主経路にモンテカルロがないこと、RViz設定のバイト一致。

非同期化で動作が滑らかになったことを、絶対姿勢誤差、分布の過信、物理到達成功の解消とは説明しない。それぞれを同じ実行の別の数値として評価する。

## マーカー相対到達と絶対姿勢の比較

ユーザーは、初期時点から物理身体がたわんでいるため、カメラ姿勢の推定誤差を未知マーカーの根元位置が吸収し、身体と目標に共通するずれが残ったまま相対的には手先が届く、という解釈を提示した。これは未知環境を含む相対観測の非同定性についての構造的な説明である。マーカー位置が上方へずれる方向・量や、今回の全誤差の原因まで、この説明だけで証明したとは扱わない。

IMUの重力方向は身体の傾きを拘束する追加情報になる。一方、重力だけではyawや絶対位置を直接決めない。同じ実行で、手先と目標それぞれの根元座標系での絶対誤差、両者の相対誤差、物理世界での到達距離を分けて記録する。マーカー単独とIMU併用の比較は、この区別に基づいて評価し、相対到達や非同期化による滑らかさを絶対姿勢推定の解決と説明しない。
