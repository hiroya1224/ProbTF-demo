# C++数値処理と取得時刻順の逐次推定

2026年10月18日のユーザー指示を記録する。実装・検証結果は作業の進行に合わせて追記する。旧共同バッチの速度やテスト結果を、この方式の速度・推定精度の証拠として扱わない。

ユーザーは「cpp にしましょう。それで、バッチ処理はこの逐次計算を繰り返し流す方式に置き換えます」と指定した。全データを使うことを優先し、処理能力が足りない場合の間引きを許可した。ただし、古い部分だけ、新しい部分だけなど、履歴の一部に偏った選択を避ける。

## 逐次更新の意味

保存された取得イベントを、元の取得時刻と同時刻内の不変sequenceで並べる。各イベントは原ID、取得時刻 \(t_i\)、その時点の送信指令 \(q_i\)、physical frame index、raw payload hashを保持する。処理開始・完了の壁時計を取得時刻へ代入しない。

前回の保持共同事後を \(\widehat\mu_{i-1}^{+}\)、その時点から今回の取得までに実際に送信した全指令区間の作用を \(F_{i-1:i}\) とする。各区間には当時捕捉したKとその出自を含める。

\[
\mu_i^{\mathrm{keep}}=(F_{i-1:i})_*\widehat\mu_{i-1}^{+}.
\]

有効な一つのセンサ観測に対し、既存の身体変化kernelによるReset候補 \(\mu_i^{\mathrm{reset}}\) と、変化事前確率 \(\rho=0.25\) を使う。未知環境の保持周辺と身体・環境の交差の扱いは既存のBFS仕様に従う。

\[
\mu_i^-=(1-\rho)\mu_i^{\mathrm{keep}}+\rho\mu_i^{\mathrm{reset}},
\qquad
\mu_i^+\propto L_i\,\mu_i^-.
\]

実装は既存の一次Bingham由来座標によるセンサ局所候補の構成・持ち上げ・正規化evidenceを使う。上式の厳密な任意非線形Bayes積分を新たに実装したとの意味ではない。新しい観測の全native成分とlog質量を使い、その一件の更新後に全within/between共分散と全リンク・未知環境の交差を含む単一内部代理へ再表現する。

\[
\widehat\mu_i^+=\mathcal P(\mu_i^+).
\]

次の観測は、この \(\widehat\mu_i^+\) から始める。batchは原イベントを一括受信するための単位である。共同バッチで使っていた、同じSTART候補から全時刻の尤度を一度に構成する処理、Resetをbatch開始へ置く処理、\(1-(1-\rho)^N\) による集約、末尾だけの内部単峰化は既定経路から外す。

IMUと画像が同じstamp/frame/commandを持つ場合も、現在の明示仕様 `per_effective_sensor_event` に従い、sequence順に別の観測として処理する。同時待ちや新たな同時刻共同更新は追加しない。通知だけ、欠測、無効観測、間引きで未融合となった観測では新しいBFS/K観測更新を行わない。

## 身体と剛性の分離

各有効観測について、実際に使用した変化混合事前と、IK・表示へ渡す単一化後の身体事後を、その取得時刻・指令・chart・全交差・質量・source IDとともに凍結する。未知環境を先に周辺化した身体の比を、当該指令 \(q_i\) における補助力学モデルで照合する。異なる時刻の観測を終端指令だけで代用しない。

\[
r_i(K)=
\frac{p_{B,i}^{+}(\operatorname{FK}(K,q_i))}
     {p_{B,i}^{-}(\operatorname{FK}(K,q_i))}.
\]

剛性workerは原順のFIFOで比因子と既存の剛性BFSを更新する。身体workerはそのevidence計算を待たず、完成した身体を制御側へ渡して次の観測へ進む。剛性結果が未完了の間は、制御は前回の完了済みKを使う。取得済み、身体処理済み、有効融合済み、K処理済みを別に記録する。新しい身体を古いK結果の到着で置換しない。

## C++移植の範囲

デモ内の数値処理を移植する。既存coreのファイルと既定法則、画像/粒子/軸サイズ、RViz設定は保護する。Pythonは取得DB、プロセス間の手渡し、既存型の構築などを担当できるが、重い数値ループを単にPythonへ呼び戻す実装をC++化と説明しない。

移植対象は、Bingham由来の回転座標、全交差を保つ再表現、候補の経路照会、およびマーカーボード中央融合の正規化定数・モーメント計算である。Python参照と同じ式・支持・近似・成分順を使い、符号・全共分散・evidence・質量の数値一致を確認する。単純な平均FKへの置換、native画像mixtureの事前縮約、新しい再線形化アルゴリズム、モンテカルロは導入しない。

全プログラムをC++へ書き換えたわけではない。逐次処理の順序管理、BFSとGaussian融合の呼び出し、既存画像姿勢推定器、K履歴管理、DB/IPCはPythonを残す。行列演算には既存NumPy/SciPyのnative処理も使う。画像検出は既存OpenCVである。今回C++へ移した箇所と、従来からnativeだった箇所を区別する。

両backendの同じ実観測列では、局所位置パラメータの最大差はMarkerで \(4.19\times10^{-10}\) m、IMU＋Markerで \(1.60\times10^{-11}\) m、全共分散の最大成分差はそれぞれ \(4.05\times10^{-12}\)、\(1.07\times10^{-12}\) だった。異なる算術実装間の丸め差は数値許容で比較する。一方、同じ実行内の推定・K検証・制御・表示は同じbackendを使い、不変lawのID・数値hash・wireを厳密に照合する。

## 過負荷時の選択

`async_execution.observation_selection.mode: all` は、全ての取得済み有効センサイベントを処理する。まずこの条件でC++版の全件再生を測った。marker画像80件は取得6.67秒分に12.98秒、IMU＋markerの120件は取得2.93秒分に8.85秒かかり、K/IPC/保存を除いても取得速度へ届かなかった。

この実測に基づき、通常実行の設定は `uniform_time`、frontier内の上限をIMU8件・画像2件とした。上限以下のセンサは全件を使う。これは1秒当たりの固定レートではなく、一回にclaimした保留履歴の数の上限である。rawはどのモードでも全件保存する。全件処理へ戻すには設定を `mode: all` とするか、ROS private parameter `~observation_selection_options` に `{mode: all}` を与える。

処理時間の実測後、必要な場合は `uniform_time` とセンサ別の `max_events_per_sensor` を明示する。上限が2件以上なら、固定したpending frontierのセンサ別取得範囲の両端を含む等時間targetを使う。両端の取得を保持し、順序と一意性を満たす選択全体でtargetとの時刻差二乗和を最小化する。1件だけなら中央時刻に近いものを選び、全取得が同一時刻ならsequence全体から等間隔で選ぶ。これは尤度や推定結果、真値による観測選別ではない。

最初の90秒試行で使ったmidpointを前から貪欲に選ぶ方式には、不規則な時刻列で偏る欠陥があった。例えば取得時刻 `[0,49.9,50.1,100]` から2件選ぶと `[49.9,50.1]` となり、100秒の履歴の中央0.2秒へ集中する。修正後は `[0,100]` を選ぶ。`[0,.01,.02,100,100.01,100.02]` から4件選ぶ場合も、前半clusterから1件・後半から3件となる旧貪欲選択を使わない。旧試行の結果は変更せず、その方式の記録として残す。観測の存在しない時間帯を埋める保証や、指令空間での多様性の保証とは区別する。

選択後も元の時刻・指令を使う。未選択のrawには `observation_fused: false` と `temporal_thinning` を記録し、そのイベントによるBFS/K更新をしない。次の選択観測までの実行区間ledgerは全て使う。間引きで観測情報が失われることを明示し、全情報融合や、元の全観測事後と同値とは説明しない。変化確率は保持した有効観測単位の既存仕様であり、未観測イベント数でhazardを勝手に増やさない。

取得範囲・選択範囲、各センサの取得数・選択数、採用/未採用ID、選択理由をbatch記録へ保存する。時間全体を覆う選択は、指令空間での励起や観測の識別力を保証するものではない。

## 検証

回帰テストは1,036件通過。C++/Pythonの同一入力比較、原t/q/ledgerと各K因子の対応、全raw/未融合の集計、両ケースの90秒RViz実走を行った。数値結果と範囲は [比較記録](validation/cpp_sequential_inference_20261018/backend_comparison.json)、[テスト記録](validation/cpp_sequential_inference_20261018/regression_manifest.json)、[90秒の観察](validation/cpp_sequential_live_20261018/OBSERVATIONS.md) に記録する。

全10,338 rawのpayload hash・spool・原t/q/frame/sequence・実ledger対応、全875表示候補の185,188,618 wire bytesと同じ不変law/勾配/Kを照合した。未融合の間引きと欠測は分けて記録している。

一方、90秒で両ケースとも物理到達は未達だった。非初期のMarker更新に約17.5 cmのリンク姿勢変化が残り、IMU併用にも約6.9 cmの変化がある。表示だけのずれではなく、同一取得qの更新前後lawに存在する。初回観測による事前からの補正と区別し、原観測との整合を追加調査する。C++化・逐次化を跳ねの完全解消と説明しない。

身体は原取得90秒まで処理したが、Kは別workerに未処理のFIFOが残った。検証用のpost-motion観察窓終了時に処理途中を保存してowned demo processesを閉じたもので、Kが数値収束した・全選択観測がKへ反映済みとは記録しない。全K入力archiveに欠番はない。後半のcoordinatorにも配信頻度低下が残り、その正確な内部処理時間を追加計測する。身体更新の高速化だけを、Kを含む全処理の実時間性能やリーチング成功の証拠にしない。

追加調査では、不変JSONの受信時の再構築と配列探索に重複した再帰処理を見つけ、候補数値を変えずに削減した。1,056件の回帰が通過し、同じ実候補の全記録JSON・candidate hashも一致した。計測と残るGC/K遅延は[IPC報告](validation/cpp_sequential_inference_20261018/IPC_PERFORMANCE.md)、回帰のsourceは[記録](validation/cpp_sequential_inference_20261018/followup_regression_manifest.json)を参照する。

間引きv2の保存済みfrontierへの選択だけの比較では、件数・原t/q対応を変えず、2件以上選ぶ全frontierで取得範囲の両端を含めた。旧方式の最小選択幅はMarker画像で取得範囲の24.8%だったのに対し、この比較では100%になった。これは同じ取得履歴の選択だけの検証であり、新しいオンライン推定・到達の結果ではない。[比較記録](validation/cpp_sequential_inference_20261018/time_selection_v1_v2_comparison.json)に範囲・原IDと全照合を保存する。

残る跳ねの[数式と実観測の診断](validation/cpp_sequential_live_20261018/noninitial_jump_diagnosis/DIAGNOSIS.md)では、原Gaussian条件付けとPython/C++再表現は一致した。一方、単一観測内で固定した一次写像の外挿差を確認した。Marker147ではlink6の実位置誤差が19.26→29.33 cmへ悪化し、次の148では28.12→17.91 cmへ戻った。単に表示やResetの重みだけで説明しない。ユーザーはこの追加調査後、同じ事前を固定して同じ観測を重複融合しない非線形更新の設計・実装を承認した。それは本書で検証したC++移植・逐次化から分ける。ここまでの一次観測更新の結果を、今後の非線形更新の性能の証拠へ付け替えない。
